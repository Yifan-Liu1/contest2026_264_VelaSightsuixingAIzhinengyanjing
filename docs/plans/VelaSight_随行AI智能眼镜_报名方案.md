### 1.3 项目名称

VelaSight 随行 AI 智能眼镜

### 1.4 一句话定位

为沟通困难人群识别表情线索并提供提示。

### 1.5 背景

现有智能眼镜大致分为三类：拍摄和音频入口型、显示通知型、云端语音问答型。它们通常存在以下问题：

- 感知和交互割裂：能够拍摄或录音，但不能联合面部表情、语气和短对话形成可用的沟通提示。
- 仍以被动问答为主：用户必须明确唤醒并组织问题，设备很少基于场景变化主动提供恰当帮助。
- 穿戴端系统成本较高：完整 Linux/Android 方案带来更高的内存、启动、功耗和物料压力，不利于轻量、长续航、低成本形态。
- 新平台复用门槛高：BK7258 具有 Wi-Fi、BLE、Camera、Audio 和硬件编解码等能力，但 openvela 尚未完成该平台适配，芯片能力不能直接转化为 openvela 生态能力。
- 隐私和社会接受度不足：第一视角摄像头和麦克风容易引发旁观者隐私担忧，需要从采集指示、最小采集、按需上传、数据过期和用户可控等方面进行产品级设计。

VelaSight 选择“先补齐平台、再构建单一核心应用”的路线。设备在用户主动触发或明确授权后采集交流对象的图像和一段短音频，上传云端；云端先以表情识别小模型与 ASR 提取线索、拼接提示词，再调用多模态大模型生成简短沟通提示（文本/TTS），回传设备展示与播报。例如，当模型发现对方可能表现出困惑时，提示用户放慢语速或确认对方是否理解；当线索不充分时，明确返回“无法判断”，不强行分类。

产品面向希望降低日常沟通负担的普通用户，也重点关注社交障碍、社交焦虑以及较难理解面部表情和语气等非语言线索的人群。在陌生人交流、面试、聚会等高压力场景中，眼镜以低打扰方式提供参考线索，帮助用户更从容地确认对方是否理解或是否适合继续当前话题。

### 1.6 价值

**技术探索价值**

- 完成 BK7258 首次 openvela 适配，验证 Cortex-M33 AP 核启动、MPU/FPU、IRQ、SysTick、Mailbox v2、PWC、日志和多核协同链路。
- 首次在该 openvela/BK7258 组合上打通 Camera、Audio 和网络数据链，为 openvela 多媒体穿戴设备提供可复现参考。
- 验证“CPU1/OpenVela 承载应用和系统能力，CPU0/原厂 CP 固件保留射频及系统控制”的渐进式移植架构。
- 首个纯 openvela 系统带 Camera 功能的智能眼镜。
- 验证“端侧轻量 + 云端小模型（表情/ASR）+ 多模态大模型”三节点协同，在 MCU 资源下以小模型降低大模型 token 消耗与延迟。

**产品落地价值**

- openvela 面向轻量化、低功耗、AI 原生 IoT 设备，采用实时内核和按需组件化配置，相比通用 Linux/Android 路线具有更小资源占用、更快启动和更清晰软硬件边界的潜力。
- BK7258 集成 Wi-Fi、BLE、多媒体接口和硬件音视频编解码，可减少外部主控和通信芯片，适合探索低成本、长续航眼镜原型。
- 通过 Tool/Skill 将采集、表情分析和提示输出组织为可控闭环，验证 openvela 主动式 AI 应用在智能眼镜上的实现方式。
- 为社交障碍、社交焦虑及非语言线索识别困难人群提供可负担、免手持、低打扰的沟通辅助原型，体现技术普惠价值。

**技术沉淀价值**

- 形成可上游化的 vendor_beken 芯片层、板级层、defconfig、构建打包链和测试基线。
- 形成 BK7258 多核 Mailbox、Camera、Audio、Wi-Fi/BLE 接入的调试方法和 AI Coding Skill。
- 形成表情识别型穿戴设备的隐私设计、端云协议、性能指标和故障降级模板。
- 形成“8.16 基础适配门禁”验收方法与实测证据基线（图像/音频/网络三格均已有实机记录）。

### 2.3 是否为待适配板

是，BK7258 DevKit 为大赛官网列出的待适配开发板，本项目执行 C 方向新硬件平台适配。

团队已开展 BSP 移植，但不具备 NuttX/RTOS 移植经验。当前已经完成：

- BK7258 物理 CPU1/AP 启动 openvela/NuttX，480 MHz 运行基线（Cortex-M33 hard-float、MPU/FPU、IRQ、SysTick）。
- Mailbox v2 基础传输、logical channel、sequence、ACK、超时、FIFO full 恢复和 12 个运行统计字段。
- AP power-up indication、2 秒 heartbeat 和 PWC boot-ready 握手。
- AP 日志经 Mailbox UART 转发到 CP 物理 UART0，并已实现全双工 console 输入（Ctrl-C/CLE 快捷键）。
- GPIO 按键（3 键低有效）、PWM/震动（1 kHz、70% 占空比 Demo 与三种应用节奏）、内核 LED 状态灯（GPIO40 红/41 绿）。
- 16 MiB PSRAM non-cacheable/XN 映射、AP 独立 heap（arena 6.4 MB）、4 个媒体 pool 和 /mnt ramdisk。
- DVP + GC2145 Camera：单帧 JPEG 480×480/640×480/864×480 实机采集（硬件编码，头修复后可解码）。
- Audio ADC 16 kHz/16 bit/单声道实机采集；Audio DAC + HT6872 单音播放实测可闻。
- Wi-Fi STA 全链路：扫描、关联、DHCP、DNS、TCP、TLSv1.2、HTTPS 200（开放热点实测；WPA2 与证书校验未验证）。

## 三、技术方案（必填）

### 3.1 总体架构

（架构图：感知层 → 系统层 → 多核适配层 → 应用层 → 云端识别层 → 大模型层 → 交互层）

端云数据流（2026-08-14 组会确定）：

- 三节点：端侧 → 云端 → 大模型。端侧上传图像（640×480 JPEG）+ 短音频（如 5 s 音频 + 约 1 fps 采样帧）；云端先跑表情识别小模型与 ASR（小模型降低大模型 token 消耗），拼接提示词后调用多模态大模型；大模型返回社交建议文本/TTS，云端转发回端侧展示与播报。
- 端侧 ai_agent 与 social-cue Skill 保留为降级路径（云端不可用时本地兜底）；提示词与 Skill 拼接在云端执行。

关键功能：

- **感知层**：Camera、麦克风、按键等输入，强调用户触发和可见采集状态。
- **系统层**：openvela/NuttX 调度、内存、驱动、网络、多媒体和低功耗管理。
- **多核适配层**：Mailbox v2、PWC、日志、Wi-Fi 虚拟网卡、BLE HCI 和 Flash 代理。
- **应用层**：板载交互界面（屏幕+三键）、Web 管理界面、KVDB 本地存储、采集与上传状态机。
- **云端识别层**：表情小模型、ASR、提示词拼接、模型路由；只返回结构化、可解释结果。
- **大模型层**：多模态表情与语气理解、沟通建议生成和 TTS。
- **交互层**：震动作为最低打扰提示，语音作为主要信息输出，屏幕展示采集/隐私状态与情绪图表，手机浏览器用于配网、配置与长内容。

关键设计原则：

- 默认不持续上传，采用按键触发的短时采集（不做常开麦克风语音唤醒；如做唤醒须用官方指定唤醒词“Hello Vela”）。
- 端侧完成采集、预处理、数据裁剪、策略控制和结果执行；识别与推理放在云端（小模型+大模型协同）。
- 原始媒体默认只驻留内存并在请求完成后释放，不建立人物或表情历史档案；历史记录落在板载 KVDB，不离开本地。
- AI 输出是辅助线索，不把表情识别结果表述为事实，不做医学、心理或身份诊断。
- 多媒体、网络、心跳和日志使用有界队列，任何非核心服务不得阻塞 PWC/heartbeat。

### 3.2 openvela 角色定位

openvela 运行在 BK7258 AP primary core，即物理 CPU1（Cortex-M33）上，当前为单核运行基线（NCPUS=1），正式兼容目标可扩展至 CPU1+CPU2 SMP（方案已冻结，bring-up 调试中）。它不是运行在 Cortex-A/Linux 环境，也不使用 Docker、systemd 或 Linux 用户态组件。

openvela 负责：

- NuttX 内核启动、任务调度、时钟、中断、MPU/FPU、内存和设备模型。
- Camera、Audio、GPIO、PWM、按键、LED 等 AP 侧驱动和多媒体数据流。
- 网络协议栈和通过 Mailbox 接入的 Wi-Fi 虚拟网卡。
- 板载 HTTP 服务器（Web 管理界面）、KVDB 本地数据库、屏幕+三键交互界面。
- NuttX Bluetooth Host 和通过 Mailbox 接入的 CP Bluetooth Controller（可选）。
- 端侧应用状态机（采集/上传/结果执行/隐私策略）；ai_agent 与 social-cue Skill 保留为云端不可用时的降级路径。
- 数据预处理、短时缓存、TLS 会话、云端请求、结构化结果执行和用户反馈。

CPU0/CP 保留原厂 Armino 固件，负责：

- CPU1 启动、系统电源/时钟协调、硬件 WDT、Flash 擦写代理。
- Wi-Fi/BLE 射频和 Controller、共存管理以及原厂底层服务。
- AP/CP Mailbox、PWC、heartbeat 和 AP 日志到 UART0 的桥接。

云端负责：

- 表情识别小模型（PMLR 2023 论文支撑）、ASR、提示词拼接与多模态大模型调用。
- 沟通建议文本/TTS 生成、账号鉴权、模型路由和表情分析请求处理。
- 对端侧（设备）与 AI 侧（大模型）分别提供接口；端侧只需上传媒体、接收文本/TTS。

## 四、难度评估与技术收益（必填）

### 4.1 创意与技术难点（按 TMG 格式输出）

#### 4.1.1 技术挑战

1. **Cortex-M33 多核 BSP 从零适配**：BK7258 尚未被 openvela 支持，且是 1CP+2AP 架构。解决思路是保留原厂 CPU0/CP 和 Bootloader，先点亮物理 CPU1 单核 openvela（已完成，480 MHz 运行基线），再逐步扩展 CPU1+CPU2 SMP（方案已冻结、实机 bring-up 调试中）。
2. **启动与内存边界复杂**：AP 镜像由 CP 启动，存在 Secure alias、双向量、Flash CRC 地址换算、AP/CP SRAM 分区、MPU 和 PSRAM 所有权。解决思路是从原厂分区生成物导出唯一布局，链接期断言，禁止 AP 清零或分配 CP 区域（已落实）。
3. **Mailbox v2 兼容**：PWC、heartbeat、日志、Wi-Fi、BLE 都依赖跨核 transport，涉及 pointer envelope、sequence、ACK、buffer ownership、reset 和 Cache 一致性。解决思路是先完成通用可靠 transport（已完成，含 12 个统计字段），再在其上分 logical channel 接入服务。
4. **Camera/Audio 首次接入 openvela**：原厂 Armino 驱动和 openvela 设备模型、线程/同步、内存接口不同，不能直接混链。解决思路是提取硬件事实和 wire ABI，按 NuttX 驱动模型重写最小 DVP/Audio lower-half。已打通单帧 JPEG（480×480/640×480/864×480）与 16 kHz 单声道采集，并修复硬件 JPEG 编码头（AC Huffman 表、SOS）问题。
5. **资源受限下的多媒体数据流**：AP 私有 SRAM 静态占用约 186 KB、SRAM heap 仅约 158 KB，图像、音频、TLS 和 Agent 并发容易耗尽。解决思路是有界 buffer pool、零拷贝所有权、低分辨率/低帧率 MVP，并将 PSRAM 作为可控媒体池而非通用 heap（已建立 16 MiB 映射、总 arena 6.4 MB 的 heap 与 4 个媒体 pool；cacheable PSRAM 与低功耗协同未启用）。
6. **端云实时性与功耗冲突**：Wi-Fi、Camera 和音频同时工作会提升功耗并争用内存/带宽。解决思路是事件触发、短时采集、批量上传、分级采样、空闲休眠和性能数据闭环。
7. **AI 可靠性与隐私**：表情和情境理解存在误判，第一视角媒体高度敏感。解决思路是结构化输出、置信度/不确定性、用户确认、显式采集状态、最小上传、TTL 和一键删除。
8. **TLS 安全加固（新增）**：当前 TLSv1.2 实测握手成功但仅加密未验证（VERIFY_OPTIONAL、无 CA bundle、无 SNTP 可信时间，板上无 RTC/NTP）。解决思路按依赖顺序推进：SNTP 校时 → 烧录 CA 根证书 → 改为 VERIFY_REQUIRED，凭证与 CA 最终依赖 SDIO flash 持久化。
9. **云端小模型与大模型协同（新增）**：表情识别小模型（PMLR 2023 论文支撑）+ ASR 在云端先行，可降低多模态大模型 token 消耗与延迟；解决思路是云端统一拼提示词、小模型输出结构化中间结果，端侧不参与提示词拼接。
10. **端云接口与多人语音对齐（新增）**：图片分辨率/格式、音频采样率、结果 Schema 需三方对齐；多人对话的说话人分离较难。解决思路是先采示例数据、接口对齐后联调；说话人分离不作为 MVP 硬要求，降级为时间轴文本直接交大模型处理，MVP 以单人场景演示。

#### 4.1.2 技术卖点

- BK7258 首个可复用 openvela BSP：不是单一应用移植，而是从启动、跨核协议、构建到多媒体/网络的系统级适配。
- OpenVela 原生 Camera 数据面：Camera 驱动和应用运行于 openvela AP，保留 CP 控制面但不依赖原 Armino AP 应用（单帧 JPEG 已实机）。
- 低资源多模态闭环：在 MCU/RTOS 级资源下完成“图像 + 音频 + 网络 + Agent + 云模型 + 反馈”链路，基础三格已实测打通，端云实联进行中。
- 主动而非纯问答：用户触发采集后，Agent 自动完成分析、置信度过滤和提示输出，不要求用户再次组织问题（Mock 闭环已运行）。
- 云端小模型+大模型协同：端侧只传原始媒体，云端小模型（表情+ASR）先行降 token，提示词拼接与 Skill 执行全部在云端，端侧保持轻量。
- 隐私数据本地化：历史记录与配置落在板载 KVDB，不离开本地；Web 管理界面（板载服务器+热点）复用行车记录仪式交互，无需开发手机 APP。
- 面向产品的隐私设计：采集可见、默认短时、用户确认、数据可删除，AI 结果明确不确定性。
- 潜在成本和续航优势：利用 BK7258 集成通信和多媒体能力、openvela 组件化和实时内核，减少通用高性能 SoC 方案的资源冗余；最终优势以实测功耗和 BOM 为准，不作未经测试的绝对结论。

### 9.2 安全和隐私

**是否涉及用户数据收集？**

是。项目在用户主动按键触发后，短时采集交流对象的人脸图像、环境声音和短对话，并上传云端多模态模型完成表情线索分析。设备还会处理设备标识、网络配置和云端访问凭据。以上数据中，人脸图像和对话音频属于敏感数据。

- 默认不持续录像或录音，每次只采集完成一次分析所需的单帧图像和短音频（约 1 fps、5–10 s）。
- 采集时通过屏幕、LED、震动或提示音明确告知；用户可随时取消，演示和测试需事先取得参与者同意。
- 原始图像和音频只在 RAM 中短时保存，请求完成、取消或超时后立即释放，默认不写入 Flash 或 SD NAND。
- 分析结果与历史记录落在板载 KVDB，不离开本地；云端只做当次推理，不做身份识别，不保存人脸模板、表情历史、人物画像或长期对话记录。
- 不做人脸身份识别，不做常开麦克风语音唤醒（麦克风不持续占用）。

**是否有安全风险？**

有。主要风险包括人脸和音频上传泄露、API Token 泄露、云端返回内容被篡改或格式异常、模型误判表情，以及 Mailbox 远端指针或 buffer 所有权错误导致设备崩溃。

- 传输加密现状如实说明：TLSv1.2 握手与 HTTPS 200 已实机验证，加密通道可用；但当前为 VERIFY_OPTIONAL，且板上无 RTC/NTP（时钟被迫置 2026）、未安装 CA bundle，属于“加密但未验证”。已按依赖顺序排期：SNTP 校时 → CA 根证书 → VERIFY_REQUIRED。完成前对外材料不得宣称“证书已校验”。
- 熵源已硬件化：TRNG 驱动 /dev/random，bring-up 以 32 字硬件熵种子初始化 /dev/urandom 熵池，消除 mbedTLS 无熵源硬阻塞。
- API Token 通过配置注入，不写入代码仓、README、串口日志或 AI Coding 日志。
- 日志对人名、设备 ID、请求地址和凭据脱敏，不记录原始图像、音频及完整对话。
- 云端结果必须通过 JSON Schema、长度和枚举校验；模型不能直接访问寄存器、执行任意 Shell 或绕过 Tool 白名单。
- 云端仅做当次推理、不落盘原始媒体；板载 Web 管理页仅限板载热点/局域网访问，接口需鉴权与参数校验；KVDB 存储不离开本地。
- 表情结果必须包含置信度；遮挡、线索冲突或低置信度时返回“无法判断”，不用于身份、人格、心理或医学判断。
- Mailbox 消息严格校验地址范围、长度、对齐、sequence 和 buffer 所有权；异常时停止请求并重置通道，不解引用未知指针。
- 网络断开、云端超时、队列满或内存不足时立即停止本次采集、释放数据并提示用户，不在后台静默重试或持续采集。
