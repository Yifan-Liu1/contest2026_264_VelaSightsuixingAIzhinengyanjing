## 一、编译 → 打包 → 烧录

```sh
# 1. 编译 AP（改过 Kconfig/defconfig 要先删 cmake_out/bk7258-ap_ai_agent）
cd /home/mi/vela_competition/contest
./build.sh vendor/beken/boards/bk7258/bk7258-ap/configs/ai_agent --cmake -j8

# 2. 把 AP raw binary 送进 SDK
cp cmake_out/bk7258-ap_ai_agent/nuttx.bin \
   /home/mi/vela_competition/bk_avdk_smp/build/openvela-ap.bin

# 3. 打包（CP + bootloader + AP）
cd /home/mi/vela_competition/bk_avdk_smp
podman run --rm --userns=keep-id -v "$PWD:/armino" -w /armino \
  localhost/bekencorp/armino-idk:1.5 \
  make -C projects/app_ab bk7258 SDK_DIR=/armino \
  EXTERNAL_AP_BIN=/armino/build/openvela-ap.bin

# 4. 确认打进去的就是刚编的那个
cmp projects/app_ab/build/bk7258/app_ab/package/tmp/app1.bin \
    /home/mi/vela_competition/contest/cmake_out/bk7258-ap_ai_agent/nuttx.bin \
  && echo "app1.bin 一致"

# 5. 烧录
cd /home/mi/vela_competition/contest/contest2026_264_VelaSightsuixingAIzhinengyanjing
sg dialout -c "VELA_ROOT=/home/mi/vela_competition \
  BK_LOADER=/home/mi/Test/bk_loader_v2.1.11.8/BEKEN_BKFIL_V2.1.11.8_20240509/bk_loader \
  ./autoflash.sh -b 1500000"
```

第 4 步不是形式主义：打包会静默复用上一次的 `app1.bin`，`cmp` 是唯一能证明
"烧的是这次改动"的东西。

**烧录前把控制台留在 CP shell。** `autoflash.sh` 靠往串口写 `reboot` 做软复位，
而 `reboot` 只有 CP 有；控制台停在 AP 的 NSH 上时会拿不到总线，提示要手按 RST。
逃回去的办法：

```sh
printf '\035.' > /dev/ttyUSB0     # Ctrl-] 松手再按 .
```

## 二、回归项

全部用 `-b`（热态）。冷态会把 Wi-Fi、provisioning、velasight 的启动开销算进帧率，
同一条命令实测能差一倍以上（480x480：冷 7.49 fps / 热 17.83 fps）。

### 2.1 硬件 JPEG，480x480 与 640x480

```sh
./serial_cmd.sh -b -w 100 -e 'agent_camera: OK' -o /tmp/r480.log 'agent_camera 480x480 n=30'
./serial_cmd.sh -b -w 100 -e 'agent_camera: OK' -o /tmp/r640.log 'agent_camera 640x480 n=30'
```

每份日志看这几行：

```sh
grep -aE 'session .* fps|stop_capture: (ring_over|jpeg chunks|validator|cycles|core clock|drain|reconcile)' /tmp/r640.log
grep -a 'structure' /tmp/r640.log | grep -ao '=no' | wc -l    # 必须是 0
```

<!-- markdownlint-disable MD033 -->

**先读这一段，否则会把好固件判成坏的。** `agent_camera` 每帧打两行，而 AP 的 stdout
要经 mailbox 桥到 CP 的 UART0，那条链路约 11.5 KB/s 且 CP 侧是**非阻塞丢弃**。后果有两个：

1. 日志里会缺行、串行，甚至在词中间截断
   （实测出现过 `structure SOF=yes DQT=yes DHT=yes SOS=ye: set_buf:`）。所以判据
   **既不能是"structure 行数等于 30"，也不能是"整行匹配 SOF/DQT/DHT/SOS/EOI 全 yes"**
   —— 两者都会把被截断的好帧判成坏帧。可靠的写法是数 `=no` 的个数，必须为 0；
2. 打印会抢 CPU、饿死跑校验的 LPWORK，于是交付率被消费端拖慢。实测同一条命令
   五次：24.36 / 25.34 / 27.34 / 28.14 / 29.18 fps（`hw_busy=0`），另有一次
   10.66 fps（`hw_busy=53`）。

所以 **`hw_busy` 是帧率数据是否可用的开关**：`hw_busy=0` 时 `measured=` 才代表驱动
能力，非 0 说明这一次被消费端拖住了，重跑，不要据此判定回归。

| 判据 | 要求 |
|---|---|
| `hw_busy` | 0。非 0 则本次帧率不作判据，重跑 |
| `measured=` | `hw_busy=0` 时不低于基线区间下界的 90% |
| `structure` 行里的 `=no` 个数 | 0（不要数行数，控制台会丢行和截断） |
| `ring_over` / `no_soi` / `short` / `hdr_fail` | 全 0 |
| `bit_fixed` | 0。**非 0 就是位对齐问题回来了**，先查启动时序（`0xF2` 门控）而不是调校验参数 |
| `bit_fail` | 允许个别（fail-closed 拒帧，不是交付坏帧）；成规模出现要查 |
| `validator avg` | ≤ 5 ms |
| `core clock measured` | 481000–488000 kHz |
| `drain spins max` | 0 |

### 两个已知、未修的问题

**480x480 帧长逐帧振荡**（17 KB ↔ 49–65 KB）。`bk7258_jpeg_enc_set_target_bitrate()`
按 `x_pixel` 分档，480/8 = 60 不在 40/80/160/200 里，落进 `default` 用了 640 档的
35 KB/20 KB；而 480x480 的自然帧长约 17 KB 低于 20 KB 下界，码率控制于是不断抬
质量、冲到 60 KB 再掉回来。原厂 `jpeg_hal.c` 的 switch 同样没有这一档，是照搬过来
的缺口。后果是 480x480 反而比 640x480 慢——多出来的 40 KB 全要走 copy + scratch +
realign。修法是加一档，但会改变画质与帧长，属产品取舍。

**640x480 的字节数对账偶有大偏差**：1–52/30 帧超出 ±64 的窗口（跑得顺时 1–5 帧，
被控制台拖慢那次 52 帧），最大约 25 KB；480x480 顺跑时是 30/30 精确为 0。所以
`CONFIG_BK7258_CAMERA_JPEG_RECONCILE` 保持关闭（只记录不拦截）——按 ±64 拦截会误杀
可观比例的帧。要启用得先把那几帧单独抓出来看，再定窗口；从"偏差随控制台拖慢而
显著变多"这一点看，它更像是交付被延迟时 span 里混进了后续帧的字节，而不是编码器
本身的问题。
